# hatch.sh v0 — the one-command hatch (2026-07-09)

**What this is.** `cabinet/scripts/hatch.sh` is the THIN orchestrator of the
already-rehearsed hatch chain. It runs the exact sequence of the
mini-hatch spec of record (2026-07-07 runbook) and
reimplements nothing — every step is an existing, proven script
(per the world-onboarding hatching plan, 2026-07-09, §7.3: "hatch.sh
ORCHESTRATES, never reimplements"). v0 is the Terminal face; the Hatch
Cabinet.app launcher (WORLD-ONBOARDING-V1B) wraps this same engine later.

```bash
bash cabinet/scripts/hatch.sh --defaults          # the non-interactive hatch
bash cabinet/scripts/hatch.sh --dry-run --defaults  # print the plan, run nothing
```

## What v0 DOES

1. **Host bootstrap** — `setup-env.sh --defaults` (with `--defaults`) +
   `setup-mac.sh --fast` (boot-path fast lane; `--check` under `--clean-room`).
2. **Instance generation** — `generate-instance.py [--defaults]` (init
   fast-lane). An inherited `instance/` triggers the rehearsed adoption path:
   auto `--adopt` under `--defaults` (archives conflicts to
   `instance/_pre-adopt-<stamp>/`, deletes nothing), otherwise it prints the
   exact `--adopt` command and stops.
3. **Activation** (runbook step 4) — writes `instance/config/active-preset`
   from the answers' `org_shape` (the generator's own mapping: portfolio →
   portfolio, functional → work; custom = named handback), then
   `bootstrap-roles.sh --roster instance/config/roster.yml` (plain call when
   no roster.yml), then `load-preset.sh`. load-preset.sh also materializes
   `instance/config/posture.yml` + `trust-ladder.yml` from their shipped
   `.example` twins when absent (consent-safe guardian posture / floor
   ladder); an existing file or symlink is never overwritten.
4. **Proofs** (runbook step 5) — P-a `null-hatch.sh`; P-b the clean-room
   pytest subset (`test_clean_room.py`, `test_no_screenpipe_in_core.py`,
   `test_no_launcher_hardcode.py`); P-c dry renders
   (`start-officer-mac.sh cos --dry-run`, `deploy-mac.sh --officer cos
   --dry-run`); P-d kill-switch drill only with `--with-drill`. Red gate =
   stop, never proceed.
5. **FIRST RECEIPT** — `first-briefing.sh --local` (genesis contract) and
   prints where the briefing landed.
   **+ DEMO receipt** — `emit-demo-receipt.sh` seeds ONE labeled demo receipt
   (`instance/memory/demo-receipt.md`): a demo:true row built via the real
   schema path (action_undo new_row + validator) and rendered by the real
   receipt renderer — NEVER journaled, the live undo journal stays empty.
   Plan step 13; move-in renumbers to 14.
6. **Flight recorder** — per-step wall-clock timings into a flight log
   (default `~/hatch-logs/hatch-<stamp>/flight.log`, step logs beside it),
   stamps `HATCH_START` / `HATCH_PROOFS_DONE` / `FIRST_RECEIPT_DONE`, and a
   printed summary table with **TTFR** (proofs-done → first-receipt) and
   total time.
7. **Failure honesty** — a failed step prints the exact failed command + its
   log path and exits 1 (composite orchestration steps additionally print
   the underlying, paste-runnable script invocation). Two documented
   warn-and-continues: no `TELEGRAM_COS_TOKEN` name in `cabinet/.env` → the
   First Mate boots Telegram-dark (rehearsal-verified) and the checklist says
   so; and the whole of the move-in (see 7b).

7b. **THE FRONT DOOR ALWAYS OPENS (2026-08-12)** — the move-in is
   **non-fatal**. Measured failure: an operator double-clicked the app
   (`hatch.sh --defaults --with-launchd`), every gate passed, and
   `deploy-mac.sh --officer cos` then died with launchd's `Bootstrap failed:
   5: Input/output error`. The move-in steps were hard `run_step` calls, so
   `step_fail` exited 1 *before* the verdict and *before* the browser
   handover: no dashboard, no password, nothing opened, "Process completed",
   and a stranded operator holding a cabinet that was in fact fully built.
   Now: the first move-in failure stops the REST of the move-in (each step
   depends on the one before it), is recorded in the flight log as
   `MOVEIN_FAILED [<step>]` with its own step log, is said once in plain
   words, and the run continues to the verdict and the browser. The app-feel
   tail also **self-starts the dashboard** when the move-in failed — nothing
   else did. The run exits **75**, not 0 and not 1.
   What is NOT softened: the real gates. Host setup, instance generation,
   activation, every proof and the first receipt still stop the run at 1,
   because without them there is no product to open.
8. **App-feel tail (Wave D, plan step 16; browser handover 2026-08-02)** —
   after the GREEN verdict, WHERE-THINGS-LIVE prints the dashboard URL
   (`http://127.0.0.1:<port>/`; port = `CABINET_DASHBOARD_PORT` env >
   `cabinet/.env` > 3100), where the briefing is readable in a browser
   (`<url>briefing`), and the Add-to-Dock/Install one-liners (Safari
   File > Add to Dock; Chrome "Install page as app").
   Then **the hatch hands over a browser instead of a terminal
   instruction**:
   - On the DEFAULT `--no-launchd` path nothing is serving yet, so the
     tail probes `/api/health` once and, if nothing answers, starts
     `start-dashboard.sh` with `nohup` into
     `<log dir>/step-dashboard.log`. That process **outlives hatch.sh** —
     the printed line carries its pid, its log path, and
     `kill $(lsof -ti tcp:<port>)` to stop it. An already-serving port is
     reused, never stacked on.
   - It drops `~/Applications/Captain's Cabinet.webloc` (tmp →
     `plutil -lint` → mv; it opens the DEFAULT BROWSER — a bookmark with
     an app-like home, not an app window; true app-feel comes from the
     printed install lines). Honest now on both paths, because a server
     really is running.
   - It waits on `/api/health` and says what it is waiting for every 60s
     (a first run does `npm ci` + `next build`), plus how to skip it next
     time. Bound: 60 tries with `--with-launchd` (~2 min when the port
     refuses, ~4 min when it accepts and hangs), 150 on the
     `--no-launchd` path it just started (~5/~10 min) — the build is
     minutes, not seconds.
   - On a FRESH instance there is no password yet — you choose it on the
     dashboard's first-open "create a password" screen — so this step has
     nothing to copy and simply hands you to that screen. If a password has
     since been set, it copies it to the clipboard via
     `dashboard-password.sh --copy`, which **never prints it** — not to
     stdout, not to a log, not into argv. A refusal there changes nothing
     else and is NOT reported as a fault (2026-08-12): the script prints the
     precise reason itself (no password yet / no clipboard / bad
     permissions), so the tail points at that line rather than guessing one,
     and the closing sentence becomes "if it asks you to choose a password,
     pick one you'll remember" instead of telling the operator to paste one
     that does not exist.
   - It `open`s `<url>onboarding` — the door, not the dashboard root.
     Auto-open is skipped over SSH, with `HATCH_NO_OPEN=1`, or where no
     `open` exists; a not-yet-up server says plainly that it is taking longer
     than expected, that nothing is broken, and where to look.

   Three ways out, all honest: `--clean-room` skips the whole step (no
   server, no clipboard, no browser, no `~/Applications` writes) — that
   is the CI/headless arm and it is unchanged from before this feature;
   `--no-browser` (or `HATCH_NO_BROWSER=1`) does the same skip on a
   normal run and still prints the manual start command;
   `HATCH_NO_OPEN=1` is the narrow one — start, wait, hand over the
   password, just don't raise a window. NEVER a gate: the tail is wrapped
   so no failure inside it can recolor the verdict or change the exit
   code.

## What v0 SKIPS (deliberately)

- **launchd move-in** — default is `--no-launchd`: nothing is bootstrapped;
  the move-in commands (runbook section 6: `deploy-mac.sh --officer cos`,
  `generate-plists.py`, `plutil -lint` + `launchctl bootout || true` +
  `bootstrap` per plist — bootout-first is deploy-mac.sh's own idiom, so
  re-runs stay idempotent — then `health-check.sh`, then `cabinet-doctor.sh`
  as final acceptance) print as an errand note. `--with-launchd` runs them.
- **GERMLINE steps are NEVER automated** — the `cabinet/mcp-scope.yml` +
  `cabinet/officer-capabilities.conf` lane-CEO entries stay Captain
  copy-paste (errand note 1), exactly like BotFather tokens and TCC clicks.
  And because they are never automated, **the chain never depends on them**
  (roster-authz, 2026-07-26): `generate-instance.py` rosters a lane CEO only
  once BOTH files already authorize it, so no officer is ever hired into a
  silent capability/MCP-scope lockout and the new `[roster-authz]` proof —
  which runs `framework/tests/test_roster_conf_lockstep.py` against the tree
  this hatch just wrote — is green by construction. Applying the rows and
  re-running the generator is how a lane CEO gets hired, always post-hatch.
- **P-d full revocation proof** — the v0 drill proves the switch flips and
  reads back; the booted-officer-refuses-tool-call proof needs a live
  officer (move-in time).
- **script(1) self-recording, native launcher, world choreography** — the
  design doc's Act I/II launcher features; v0 keeps the flight recorder only.

## Flags

| Flag | Meaning |
|---|---|
| `--defaults` | Non-interactive everywhere: `setup-env.sh --defaults`, `generate-instance.py --defaults`, auto-adopt on an inherited `instance/`. |
| `--clean-room` | Throwaway-HOME tolerant; no installs (`setup-mac.sh --check` must find deps present); never touches launchd or the live Redis (load-preset's expected-active marks point at an unused port, `HATCH_CLEANROOM_REDIS_PORT`, default 6399); DB schema apply stays load-preset's own best-effort skip; `CABINET_RUNTIME_DIR` is routed into the run's scratch area beside the flight log (`<log dir>/cabinet-runtime`; an ambient override is respected **unless it resolves to — or nests under — the live default**: a routed runtime dir *or flight-log dir* landing on `/tmp/cabinet-runtime` in any spelling — the `/private/tmp` alias, slash runs, `.`/`..` segments and symlinks are normalized before the compare — is refused, exit 64, *before anything is written*, the flight-log parent included. So a `--flight-log` directly in `/tmp` refuses — it would route the runtime dir onto the live path — as does a `--flight-log` inside `/tmp/cabinet-runtime` itself — flight.log + step logs would pollute the governance dir — and an ambient override aimed at or under the live dir: the containment must not self-defeat, adversarial fixes 2026-07-10) so the live `/tmp/cabinet-runtime/{constitution.md,safety-boundaries.md}` — the files officers read at boot — are never written (containment fix 2026-07-10, PC-B verifier follow-up (a); the routed path prints in the clean-room banner and lands in the flight log). Also refuses to run inside a git work tree whose `instance/config/platform.yml` is git-tracked with a real deployment config (>50 lines) — a hatch there rewrites the checkout's tracked instance config in place (seam 3, hardening C11 2026-07-11, lesson `hatch-hatches-the-tree-it-runs-in`); hatch from a throwaway scratch **export** — `mkdir -p /tmp/hatch-scratch && git archive HEAD \| tar -x -C /tmp/hatch-scratch`, then `git ls-files -c -i --exclude-standard > /tmp/hatch-scratch/cabinet/scripts/shipped-ignored-paths.txt` (the export is gitless, so `null-hatch.sh` re-derives shipped-vs-deployment-local from `.gitignore` and without that list deletes force-tracked shipped content — dashboard officers pages, `memory/tier3/`, `deployment-status.md`; `egg-export.sh` writes it for a real egg) (verify pass 2026-07-11: a plain `git clone` of this repo tracks the same 337-line platform.yml and refuses identically, so a clone needs `HATCH_ALLOW_TRACKED_INSTANCE=1` — acceptable only because the clone is throwaway) — or set `HATCH_ALLOW_TRACKED_INSTANCE=1` if the tree really is the hatch target; fresh hatch targets (no git tree / no tracked long platform.yml) are unaffected. **Known residual seam** (recorded 2026-07-11, deliberately in-scope-limited per hardening Brief 1: clean-room containment only): the tracked-instance refusal guards `--clean-room` runs — a plain non-clean-room `hatch.sh --defaults` from such a checkout still rewrites the tracked platform.yml in place. Refuses `--with-launchd`/`--with-drill` (exit 64). |
| `--dry-run` | Print the full numbered plan + errand notes; execute nothing; exit 0. |
| `--no-browser` | Skip the browser handover at the end: no dashboard start, no health wait, no clipboard, nothing opened. The chain and every gate are identical either way. `HATCH_NO_BROWSER=1` is the env equivalent (what CI sets); `--clean-room` already skips the tail. The narrower knob is `HATCH_NO_OPEN=1`: still start the dashboard and hand over the password, just don't raise a browser window. |
| `--with-launchd` | Run the move-in (runbook section 6) after the first receipt. **Never fatal** — a failure is recorded, said plainly, and the browser still opens; the run exits 75. Default: deferred checklist item (`--no-launchd`). |
| `--with-drill` | Include P-d: kill-switch activate → assert ACTIVE → deactivate → assert INACTIVE against `REDIS_URL` (default `redis://localhost:6379`). Halts a live fleet by design — fresh boxes only. |
| `--flight-log <path>` | Flight log file; step logs land beside it. Ignored by `--dry-run` (nothing executes). Relative paths resolve against the repo root (warned on stderr). |
| `--help` | Usage. |

Exit codes: `0` green · `1` step failure · `64` usage/flag conflict ·
`75` hatched and the front door opened, but an OPTIONAL background helper
(the move-in) did not start. Scripting that asks "is there a working cabinet"
treats 0 and 75 alike; scripting that manages the fleet treats 75 as "retry
the move-in" (sysexits `EX_TEMPFAIL`). The app-shell runner passes it through
and says so in plain words.

## The end-of-run checklist (printed by every completed run and every `--dry-run`; human-only, numbered)

Called *errand notes* in the code (`hatch-lib/errands.sh`) and **"YOUR
CHECKLIST"** on screen — see "Operator copy" below. A failed run prints the
failure block + flight summary instead; the checklist returns when the chain
completes. A failed *move-in* is not a failed run: the checklist still
prints.

1. **Germline scope lines — OPTIONAL, blocks nothing** — copy-paste the
   generator-printed lane-CEO entries into `cabinet/mcp-scope.yml` +
   `cabinet/officer-capabilities.conf`, then re-run `generate-instance.py`
   (that re-run is what HIRES the lane CEO) and `bootstrap-roles.sh --roster`.
   Fresh clones are not schg-locked. Until then the lane CEO is generated but
   deliberately un-rostered; the Chair-only hatch completes green.
2. **First Mate bot token** — @BotFather → `cabinet/.env` as
   `TELEGRAM_COS_TOKEN=…` (chmod 600); `VOYAGE_API_KEY` optional
   (keyword-only degrade without it).
3. **TCC grants** — `grant-mac-permissions.sh`, only if calendar/computer-use
   is wanted; not in the base hatch.
4. **Move-in** — the launchd sequence above (omitted when `--with-launchd`
   already ran it).
5. **Healthchecks.io** — create checks per `cabinet/services.yml`
   expected-floors and ASSIGN ALERT CHANNELS; keys into `cabinet/.env`.
6. **Germline lock** — post-hatch Captain act:
   `sudo bash cabinet/scripts/germline-lock.sh lock`.

## Operator copy (2026-08-12)

Everything hatch.sh prints **on screen** is written for whoever double-clicked
the app, because on the app path that is the only person who reads it. The
technical record did not move — it is in the flight log, the per-step logs and
the printed plan, all unchanged in substance.

| Was | Is |
|---|---|
| `HATCH v0 — recording to <dir>` | `SETTING UP YOUR CABINET` + "This takes a few minutes. You don't need to do anything" |
| `ERRAND NOTES (human-only steps…)` / `ERRAND 1 —` | `YOUR CHECKLIST — the few things only you can do` / `1.` |
| `WHERE THINGS LIVE (minute one)` | `WHERE THINGS ARE` |
| `HATCH VERDICT: GREEN (v0 chain complete)` | `YOUR CABINET IS READY` |
| `WARN: TELEGRAM_COS_TOKEN is not named…Telegram-dark` | "there's no Telegram bot token yet, so your Cabinet won't be able to message you on Telegram" |
| `[app-feel] AMBER: dashboard not reachable yet` | `[opening] your Cabinet is taking longer than expected to answer… Nothing is broken` |
| `[app-feel] password not copied — get it with: …` | `[opening] nothing was copied to your clipboard — the line above says why. A brand-new Cabinet asks you to choose a password on its first screen.` |
| `[app-feel] bookmark:` / `dashboard starting` | `[opening] shortcut saved:` / `starting your Cabinet` |
| step descriptions (`P-a null-hatch gate (egg boots with NO captain data)`) | plain (`safety check: a brand-new Cabinet starts with none of your data in it`) |

The same pass covers the app shell (`cabinet/scripts/appshell/`): the .app
dialogs ("Set up Captain's Cabinet", "Let it keep working while you are
away?", "Your Cabinet is already here") and the runner's first and last
lines. The runner still emits **exactly one** end-of-run notice (exit code +
log paths, APPSHELL-V05 spec 3.5) — now phrased for a person, and aware of
exit 75.

Words that stay: filenames, env-var NAMES, and commands the person has to
type (`--with-launchd`, `cabinet/.env`, `TELEGRAM_COS_TOKEN`). Words that
went: hatch, move-in, launchd, errand note, measurement-plane plists, v0
chain, AMBER, First Mate, egg.

Pinned by `cabinet/scripts/tests/test_hatch_dry_run.py` (no `ERRAND` in the
plan output), `test_hatch_app_feel.py` (no `AMBER` in the wait fallback) and
`test_hatch_movein_nonfatal.py` (no jargon in the closing note).
