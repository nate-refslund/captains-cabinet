# Hero demo — "a goal at night, receipts in the morning" (2026-07-10)

Perfect Cabinet Wave B demo kit (egg ledger row PC-B scope item 7). The
demo's one sentence: **you hand the cabinet a goal before bed; in the
morning you get one briefing whose every act carries what / why / cost and
a working undo handle.**

Two variants, never mixed:

| Variant | Data | Screenshots |
|---|---|---|
| **PUBLIC (Testburg)** | 100 % synthetic — a scratch instance + `cabinet/fixtures/testburg/` | allowed, after the review step below |
| **PRIVATE (live cabinet)** | your real estate | **NEVER for public use** — live artifacts stay on the box |

Every command below was run verbatim against this checkout on 2026-07-10
(scratch instance + demo dashboard); expected outputs are quoted from those
runs.

---

## A. PUBLIC variant — scratch Testburg instance

Work from the repo checkout; the scratch instance lives OUTSIDE it. No
Redis, no Telegram, no launchd, no network needed (the genesis brief takes
its honest-IOU lane offline).

### A0. Stage a scratch instance

```bash
SCRATCH="$(mktemp -d)/testburg-demo"
mkdir -p "$SCRATCH/instance/config"

cat > "$SCRATCH/instance/config/cabinet-init.answers.yml" <<'EOF'
# Synthetic demo captain (Testburg vocabulary — never real values)
cabinet:
  id: testburg
  mode: single
  org_shape: portfolio
lanes:
  - slug: bakery-site
    name: Bakery Site
    repos: [bakery-site]
  - slug: newsletter
    name: Newsletter
    repos: []
EOF
```

(For a REAL first-time setup this file comes from the cabinet-init
interview / `cabinet/scripts/generate-instance.py --defaults` — see
`docs/runbooks/hatch-v0-2026-07-09.md`. The demo stages it directly so the
runbook is self-contained.)

### A1. NIGHT — hand the cabinet the goal

Two equivalent file entry points (the Telegram chair DM is the PRIVATE
variant's input):

**(a) The focus letter** — genesis reads it and anchors its proposals:

```bash
cat > "$SCRATCH/instance/config/onboarding-focus.md" <<'EOF'
Tonight's goal: get the bakery-site ready for the Saturday opening — menu,
hours, and the order form — and stage newsletter issue 1 for my review.
EOF
```

**(b) A draft outcome card** — append your goal as a propose-only row to
`$SCRATCH/instance/config/outcomes-proposed.yml` (after A2 has created it;
`status: draft` + `captain_ratified: false` — the mission compiler never
reads this file, so nothing self-activates). Verified: a hand-added
"Saturday opening goes smoothly" card renders in the next briefing.

### A2. NIGHT — the org proposes (genesis)

```bash
cd <repo checkout>
env CABINET_ROOT="$SCRATCH" \
    CABINET_GENESIS_NET_HOST=127.0.0.1 CABINET_GENESIS_NET_PORT=1 \
    python3.12 -m framework.onboarding.genesis
```

The two `CABINET_GENESIS_NET_*` vars force the offline drill so the demo
never needs the claude CLI: the research brief takes the HONEST-IOU lane.
Expected: exit 0 and JSON reporting `"proposal": {"status": "written", …,
"cards": 4}` and `"brief": {"status": "iou", … "reason": "network
unreachable"}`. Artifacts land at:

- `$SCRATCH/instance/config/outcomes-proposed.yml` — 4 propose-only cards
  (two lane cards citing your focus letter + the two standing org cards)
- `$SCRATCH/instance/memory/library/genesis-research-brief.md` — the IOU
  note (`status: iou-queued` frontmatter; with a logged-in claude CLI and
  no NET override you get the real brief instead, `status: delivered`)

### A3. MORNING — the briefing receipt

```bash
env CABINET_ROOT="$SCRATCH" \
    python3.12 -m framework.frontdoor.run_briefing --now --local-render
```

Expected: exit 0; JSON with `"sent": false`, `"local_render": true`,
`"drained": 6` (4 cards + 2 FYI lines), and `"receipt_path"` pointing at

- `$SCRATCH/instance/memory/first-briefing-<UTC date>.md` — the briefing:
  header `# First briefing — <date> (LOCAL-FIRST receipt)`, then every
  proposed card as WHAT / WHY / PROOF-expected with
  `captain_ratified: false`, your focus letter quoted in the
  captain-loop card's WHY. Nothing was sent anywhere (`allow_sends`
  stays false; Redis untouched).

This is the morning artifact: open it, read the cards, and rule on them
(ratify by moving a row into `instance/config/outcomes.yml`).

### A4. MORNING — the would-be action cards (eyeball gate)

```bash
env CABINET_ROOT="$SCRATCH" \
    CABINET_VAULT_DIR="$SCRATCH/vault" \
    CABINET_SHARED_ENV="$SCRATCH/no-shared.env" \
    python3.12 framework/acting/run_action_lane.py --dry-run
```

`--dry-run` is the lane's write-free eyeball gate: gather + propose +
print, no Telegram, no ledger, no Redis writes. On a fresh scratch
instance the vault is empty, so the verified output is the honest empty:

    done: no fresh signals in window

(exit 0). On an estate with signals it prints `DRY RUN — N card(s) would
present:` followed by the rendered cards. The two extra env vars pin the
vault and shared-credentials lookups inside the scratch dir so a demo run
can never read the box's real estate. Note: the lane takes a singleton
lock at `/tmp/cabinet-action-lane.lock`; if a live lane holds it you get
`done: another action-lane run holds the lock` — harmless, re-run later.

### A5. The receipts + governance visuals (Testburg fixture)

The scratch instance above has proposed but not yet ACTED, so its journal
is empty — day-zero honesty. The screenshot-able acted story ships as the
Testburg fixture; serve it:

```bash
bash cabinet/scripts/demo-dashboard.sh          # 127.0.0.1:3199
bash cabinet/scripts/demo-dashboard.sh --stop   # tear down
```

The script stages `cabinet/fixtures/testburg/` into a scratch dir (dates
rebased single-pass so the undo windows are genuinely active on any demo
day), points the dashboard's file surfaces at it (`CABINET_UNDO_DIR`,
`CONFIG_PATH`, `ACTIVE_PROJECT_FILE`, `PROJECTS_DIR`), and starts the dev
server with an allowlist env — no `REDIS_URL`, so every `lib/redis.ts`
consumer stays on its mock branch. Login password: `testburg-demo`.

- `http://127.0.0.1:3199/receipts` — six Testburg receipts: what (plain
  language) / why / cost (attributed `~$0.0148 — 1930 in / 210 out tokens
  (lane-metered)` AND honest `cost unattributed`) / undo state (active
  with hours left, one `undone at …`, one `DEMO`-badged seeded row).
  Badge timing: the rebase puts the earliest receipt's undo horizon at
  `<demo-day>T06:10Z`, so runs before ~06:10 UTC show every non-undone
  receipt as active; if the demo needs an `expired` badge on screen, run
  later in the day or use `--no-rebase` (fixed 2026-07 story clock —
  guaranteed expired once real time is past the 2026-07-10/11 horizons).
- `http://127.0.0.1:3199/governance` — the REAL constitution + safety
  docs from this checkout (the PC-B mock-kill). Screenshot the TOP cards
  only — the lower editors render this checkout's real files (A6 gate 3;
  the server's startup banner carries the same warning).

Two known limits of the served demo (cross-area fixes flagged in the
Wave-B report; both re-checked 2026-07-10):

- **`/world` is NOT part of the synthetic estate — never open or
  screenshot it in a public demo.** The world engine route bypasses the
  stage: it builds its own redis client (localhost default, outside the
  allowlist guarantee) and reads THIS checkout's live world surfaces
  (`instance/config/outcomes.yml`,
  `shared/interfaces/world-chronicle.jsonl`), so it renders live-estate
  data even under the demo server. (`CABINET_WORLD_OUT_DIR` in the demo
  env is writer-side belt-and-suspenders for shelled-out python, not a
  dashboard reader.)
- **The nav's project selector renders the dashboard's built-in mock
  vocabulary** (`actions/projects.ts` mock branch — currently a real
  product name), not the fixture's Testburg identity — keep it out of
  frame (A6). The staged `active-project.txt` + `projects/testburg.yml`
  cover the env-honoring file readers (`lib/config.ts`) only.

## B. PRIVATE variant — the live cabinet (never screenshot for public)

Same story, real estate. Everything below shows YOUR data — treat every
artifact as private; nothing from this variant is ever captured for public
use.

1. **NIGHT — goal input:** DM the chair bot your goal in the Telegram
   binder (the chair stages it into the intake), or append a draft card to
   `instance/config/outcomes-proposed.yml` in the live checkout exactly as
   in A1(b).
2. **MORNING — briefing:** the scheduled frontdoor briefing arrives on
   Telegram (launchd-owned; see `cabinet/scripts/run-frontdoor-briefing.sh`).
   To force one locally instead: the A3 command in the live checkout
   WITHOUT `--local-render`'s scratch root — note a live `--now` run
   drains the real intake and (when `allow_sends` is configured) sends.
   For a no-side-effects look, prefer `--local-render`: it composes from
   genesis surfaces only and never touches the intake.
3. **MORNING — receipts:** acted cards from the night carry undo handles;
   `/receipts` on the live dashboard (port 3100) renders the real journal
   (what / why / cost / undo; any demo-stamped row would be badged, as
   defense-in-depth). On day one — before the org has acted on anything
   real — the live journal, and therefore live `/receipts`, is honestly
   EMPTY. Undo is a reply verb in the Telegram binder (`undo <pid>`),
   never a dashboard button.
4. The seeded day-one receipt on a fresh hatch comes from
   `cabinet/scripts/emit-demo-receipt.sh`: the row is built and validated
   through the real schema (explicitly `demo: true`, inverse op `none` —
   it never claims an undo it does not have) but is **never appended to
   the undo journal** — the whole demo artifact is the DEMO-headed
   receipt FILE at `instance/memory/demo-receipt.md`, next to the first
   briefing. The Testburg fixture's journaled `demo: true` row is a
   fixture-only exercise of the `/receipts` demo-badge path, not a model
   of live behavior (fixture README).
