## Mission

Stand up a self-improving AI organization on a dedicated Mac Mini that owns one software product end-to-end — build, deploy, operate, support — with machine-verified evidence as its primary trust supply: the Evidence Engine of blueprint §4. A product org has what the personal clone never had: abundant, adversary-resistant, machine-checkable ground truth (CI verdicts, deploy states, PR merge/revert, error-budget burn, support-thread resolution). This plan closes the self-improvement loop on the live MacBook deployment first (Gates 0–3), so evidence continuity is never severed — the twice-paid n=0 lesson — and births the Mini clean at Gate 4: fresh graduation ledger, model baseline stamped, a credential-holding executor as the only egress, an eval-gated self-modification pipeline as the estate's most protected asset, and the Captain (Nate) as a metered two-way resource whose attention is spent only where machines cannot check.

## Definition of Highest Potential

**North-star metric: verified outcomes per Captain-minute** (blueprint §4.10) — ledger-verified product outcomes (deploys held, incidents resolved, support threads closed, CI-green merges on non-test-touching PRs) divided by measured Captain attention (verdict count × handling time + debt-queue session time). The plan reaches its highest potential when this ratio trends up across two consecutive scorecard periods while autonomy coverage rises and interventions/day falls — the M4 compounding criterion.

You know you're there when:

1. **The Mini survives 30 unattended days** — watchdogs green, probes writing on cadence, zero silent job deaths, and any component starvation pages within its freshness window (principle 7: built = scheduled + fed + watched).
2. **≥3 machine-verifiable action classes run at `auto` behind veto windows** — CI-gated commits, preview deploys, board moves — each graduated from ≥20 machine verdicts with fitness (`outcome_held × review_confirmed`) > 0, while judgment lanes (external comms tone, compliance wording, prioritization) remain honestly Captain-gated. Asymmetric autonomy is the evidence engine working, not a defect.
3. **The Gate has demonstrably rejected self-changes** — gate throughput shows admitted AND rejected changes with lineage tags, proxy-vs-holdout divergence below alarm threshold, and at least one Goodhart attempt (synthetic or real) caught by the test-diff ceiling class or the read-isolated holdout.
4. **Every external side effect is a hash-locked outbox row** — zero sends outside the executor in audit, every send a label by construction, and the ledger-liveness dead-man has never fired for real (but quarterly drills prove it would).
5. **Captain attention is under budget and two-way** — escalation rate <10% of actions, no Captain-debt item older than 7 days, weekly brief rendering the raw scorecard vector with trends (no composite hiding regressions).
6. **A second product onboards through the staged SOP** (interview → shadow-week dossier → propose-only n≥20 → per-cell graduation) with zero framework code changes — product is a parameter, not a fork.

And the honest expectation to hold against it (blueprint §1): with the loop closed, machine-verifiable action classes graduate in **weeks** at product-traffic volume, while judgment classes stay Captain-gated far longer — possibly forever on a compliance product. If judgment lanes are still propose-only at M4, that is the design working; the failure mode to actually watch for is a *machine* lane still unmeasured at M2, which means a probe or the join is broken, not the world.

### B4.7 spec — executor + hash-locked outbox (the hard ceiling becomes physics)

```sql
-- CC/cabinet/cache/outbox.sqlite3  (WAL; busy_timeout>=5000 every connection; BEGIN IMMEDIATE writes)
CREATE TABLE outbox (
  id             INTEGER PRIMARY KEY,
  proposal_id    TEXT NOT NULL UNIQUE,          -- the B2.1 correlation id
  channel        TEXT NOT NULL,                 -- resend | graph | telegram | github_release | vercel_promote
  recipient      TEXT,
  payload_json   TEXT NOT NULL,
  payload_sha256 TEXT NOT NULL,                 -- hash-lock: exactly what the Captain saw
  status         TEXT NOT NULL DEFAULT 'proposed'
                 CHECK (status IN ('proposed','approved','executed','verified','vetoed','expired','failed')),
  approval_token TEXT,                          -- HMAC-SHA256(exec_secret, proposal_id || payload_sha256)
  approved_at    TEXT,
  execute_after  TEXT,                          -- the veto window (B3.3); NULL = not yet approved
  executed_at    TEXT,
  verified_at    TEXT,                          -- set by probes superseding to 'verified'
  execution_receipt TEXT,                       -- provider message id / deploy id
  created_at     TEXT NOT NULL DEFAULT (datetime('now'))
);
```

- **Separation:** the executor runs as macOS user `cabinet-exec` (own LaunchAgent, own Keychain holding RESEND key + Graph credentials + any deploy tokens). Officers run as `cabinet` and can only INSERT `proposed` rows (0600-style write isolation on the approval columns via a trigger + the executor being the only writer of `approved+` states — an officer running as the same user could otherwise forge approval rows; companion broker finding).
- **Token mechanics:** at approve time, the verdict binder (F0.7, in-process with the Captain's decision) requests `approval_token` over a one-way local socket from the executor's token service — `HMAC-SHA256(exec_secret, proposal_id || payload_sha256)` where `exec_secret` exists only in cabinet-exec's Keychain. Officers cannot mint tokens; a payload edited after approval changes the hash and is refused + paged.
- **Execution:** only rows with a valid token, past `execute_after`, and with the Captain channel confirmed live (B3.3 + B4.8 heartbeat) execute. Crash-safe ordering: mark `executed` + receipt in the same transaction as the provider call's success path; failures go to `failed` with a dead-letter alarm — never a silent drop.
- **Every send is a label by construction** — the `proposed→approved→executed→verified` chain is the gate-owns-ledger invariant expressed as physics. Migration is the one joint move of B4: the pre-B4.7 `deliver_draft` direct path stays behind a flag until the outbox chain passes its drills, then is deleted with a CI tripwire (one joint per function; evidence continuity verified as an explicit gate).

### B5.1 spec — gate-runner admission sequence (deterministic, fail-closed at every step)

For every candidate self-modification PR (branch prefix `self-mod/`), `framework/gate/runner.py` executes in order; ANY step failing ⇒ `gate_rejected` event + PR blocked; no step skippable:

1. **Provenance check** (B5.9): candidate's evidence chain free of `untrusted-external`, or Captain authentication attached.
2. **Class check:** change-class looked up (playbook-delta / skill / policy-yaml / tool-desc / memory-promotion); germline paths refused outright (Captain-only); monolith lint for playbook deltas (B5.5).
3. **Fixture integrity:** SHA-256 checksums of `memory/gate-fixtures/cases/` verified against the committed manifest; mismatch = CRITICAL (someone edited the evidence).
4. **Balanced probe:** run previously-failing + previously-passing case sets against the candidate; zero-regression budget on the passing set.
5. **pass^k:** k=3 repetitions on behavioral cases; all three must pass per case.
6. **Cost gate:** tokens/task on the probe run vs baseline; >15% rise blocks.
7. **Holdout:** decrypt in-process (B5.2), run, record pass-rate; update proxy-vs-holdout divergence stat; alarm threshold check.
8. **Credit check** (B5.8): completed within budget; if credit exhausted mid-run the whole run voids (never a partial certification).
9. **Apply path:** change-class at ≥3 confirmed / 0 wrong / reversible ⇒ auto-apply + lineage tag (B5.10); else emit a one-tap ratification card via the outbox.
10. **Ledger:** `gate_admitted`/`gate_rejected` event with case counts, divergence, cost delta, lineage tag — feeding O6/O7 in the scorecard.

**Exit criteria (Gate 5):**
1. One self-change **admitted** and one **rejected** through the full gate (balanced probe + regression budget + pass^k + holdout + cost), both visible on the ledger with lineage tags.
2. Proxy-vs-holdout divergence alarm test-fired (B5.2).
3. Credit-exhaustion drill passed with fail-closed semantics observed (B5.8).
4. Ingestion-provenance staged-injection drill passed (B5.9).

**Rollback note.** The Gate fails closed by construction: disabling the gate-runner halts auto-applies entirely — there is no regression path to ungated application (that path was removed by B2.11 + B5.10).
