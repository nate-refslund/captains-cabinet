# CI bill — the cuts that provably lose no coverage (2026-07-29)

Follow-on to `docs/plans/ci-cost-2026-07-28.md`, which measured the bill and
left a ranked backlog. This lands backlog item 1 and repairs two sensors found
while doing it. It deliberately does **not** land the two biggest levers,
because neither can be proven safe today, and a saving bought with signal is
not a saving.

Standing constraint, unchanged: **a cheaper CI that catches less is not a
saving.** Every removal below names what still catches the failure class.

---

## 2. What landed

### 2.1 `clean-room-foundation` + `clean-room-source` deleted — 1,643 min/mo (6.9%)

Both were **strict subsets** of `cabinet/scripts/null-hatch.sh`, which the
`null-hatch` job runs on every event. Established by reading both texts, not by
comparing names:

- `clean-room-foundation`'s only work step —
  `pytest framework/tests/test_no_launcher_hardcode.py framework/tests/test_clean_room.py -q`
  — is null-hatch stage 1/4, character for character.
- `clean-room-source`'s four work steps are null-hatch stages 2/4, 3/4 and 4/4.

The composed gate is **stronger** on three axes, which is why this direction is
safe and the reverse would not have been:

1. it runs against the **committed** tree (`git archive HEAD`), so a
   working-tree-only pass cannot certify it;
2. it uses a **throwaway `$HOME`**, where `clean-room-source` ran
   `rm -rf "$HOME/.screenpipe"` unsandboxed against the real runner home;
3. its CORE import list carries **`framework.evolution.contracts`**, which the
   in-workflow copy did not. The hand-copied twin had already drifted *weaker*
   than the script — and it was the copy branch protection required. Deleting
   it removes a divergent duplicate, not a check.

**What still catches what.** A hardcoded launcher name in `framework/**` → the
ratchet in stage 1. A captain-identity leak into the fidelity prompt →
`test_clean_room.py`, same stage. A personal-source resolver regression →
stage 2. A screenpipe import creeping back into framework CORE → stage 3, under
a present-but-unreadable `~/.screenpipe`, with one module *more* than before.
The framework meta-ratchets (1,247 ids) → stage 4.

**Attribution.** What was per-job signal is per-stage signal: `null-hatch.sh`
prints `[1/4]`…`[4/4]` with the seam name.

### 2.2 `zizmor` folded into the `gitleaks` job — 709 min/mo (3.0%)

Both zizmor invocations still run, once each, in the same run, on the same
tree, with the same flags and the same pinned version (1.16.3). The only thing
deleted is a second job wrapper: two jobs billed two whole minutes to do 21
seconds of analysis.

**Why this pairing.** Both are static security gates over committed bytes,
neither needs a service container, and the job's `fetch-depth: 0` — which
gitleaks needs for the nightly full-history sweep — costs zizmor nothing.
Folding them into a test job would have buried a secret scan behind a
four-minute proof that can time out ahead of it.

**Why the job kept the name `gitleaks`.** The 2026-07-28 audit parked this cut
because it "renames required status checks". That turned out to be avoidable
and is the crux of the design: retiring a context is a **removal**, which no
in-flight PR can trip over, whereas a new context (`static-gates`) could never
be reported by an open PR's older workflow and would have blocked the entire
queue — with eight PRs draining, a fleet stall. The name is now narrower than
the job. That is deliberate, documented at the job, and cheaper than the stall.

**Attribution.** Every folded step carries `if: !cancelled()`, so a leak does
not hide a workflow finding and a workflow finding does not hide a leak. The
secret scan runs first so nothing downstream can pre-empt it.

### 2.3 Branch protection: three contexts removed, none added or renamed

Before: `ci, framework-tests, clean-room-foundation, clean-room-source,
null-hatch, gitleaks, zizmor` · `strict: true`.
After: `ci, framework-tests, null-hatch, gitleaks` · `strict: true`.

Every assertion the three removed contexts carried is executed by a retained
required job on the same tree in the same run. Self-ratified per the 2026-07-07
full-autonomy grant + the 2026-07-21 ownership-on-GO ruling; recorded here and
on the `CI-IMMUNE-SYSTEM` ledger row, whose `gate_cmd` names the old set and is
now marked superseded (re-running it verbatim would read red on a change that
removed no assertion — the exact class this repo keeps paying for).

### 2.4 Two sensor repairs, both cost-neutral

**`Collection census` could not fail.** GitHub's default step shell is
`bash -e {0}` and this workflow sets no `defaults.run.shell`, so with no
`pipefail` the exit status of `pytest --collect-only -q | tail -2` is `tail`'s
— always 0 — and pytest's exit 2 on "Interrupted: N errors during collection"
was discarded. Proven by execution, both directions, 2026-07-29:

```
bash -e -c 'python -c "sys.exit(2)" | tail -2'          -> step exit 0
bash -e -c 'set -o pipefail; ... | tail -2'             -> step exit 2
control, no pipe                                         -> rc 2
```

Both blind analyses recommended **deleting** this step for its 13s. That is the
wrong repair: its stated job — make collection drift visible — is real, and it
costs 13 seconds. `set -euo pipefail` arms it instead, and
`if: !cancelled()` was added to the following `Framework test suite` step so an
armed census cannot skip the suite behind it.

**Still unasserted, named rather than papered over:** the collected *count*.
The fidelity conftest `collect_ignore`s 19 flavor-A-coupled modules on every CI
runner; nothing pins a floor, so that set could grow and no gate would object.
Arming the error path does not close that hole. Tracked in §5.

**`Dashboard vitest` had no `!cancelled()` guard** — the only test step in `ci`
without one, so a failing typecheck *skipped* 138 vitest files including the
world pixel gate, and nothing said so. This is the same one-red-hides-the-next
class the workflow documents at length two steps later. Fixed.

## 3. Result

| | trailing 30d | one full pass, today's rate |
|---|---:|---:|
| before | 23,895 min | 60 min |
| after | 21,543 min | 57 min |
| saved | **2,352 min (9.8%)** | **3 min (5.0%)** |

Both figures computed the same way (`ceil(job_seconds/60)` per job). The two
percentages differ because the four sub-minute jobs were a larger share of the
bill when the big jobs were smaller; the *forward* saving is the 3 min/pass
figure, which at the last two days' run rate (~93 runs/day) is ~8,400 min/month
and at the prior ~25 runs/day is ~2,250.

**No assertion was removed.** Every command that ran before this change still
runs, once, in the same run, on the same tree. Two commands that could not fail
now can.

## 4. Where the two blind analyses diverged, and which side the evidence took

**`cognitive-phase4` off PRs → master-push + nightly.** One arm proposed it
(~1,400 min/mo) on a measured 0.8% churn rate in the frozen COG-4 scope; the
other measured 16.6% over 30 days and 23.9% over 7, and refused.

**Followed the arm that refused, on evidence neither arm raised.** The
structural argument settles it before the churn numbers do:
`tree-dedupe`'s skip is licensed by a *run-level* success, which the job's own
header notes is stronger than the required-check set precisely *because* it
includes `cognitive-phase4`. Move the gate off PRs and either (a) it is exempted
from the dedupe and every master push pays 11 minutes — 447 pushes/month, more
than it costs on PRs — or (b) it honours the dedupe, in which case the deduped
master lane skips it and the gate is nightly-only. The proposal cannot save
money and keep the gate at the same time. The churn dispute is then moot, but
the higher figure is the better-evidenced one: it was taken with a positive
control after a first attempt returned a vacuous 0.

**`Cabinet script tests` under `pytest-xdist`.** Both arms ranked it #1
(3,570-11,258 min/mo) and both refused to certify it. So does this one — see §5.

**Caching apt/pip.** Both arms costed it at 300-795 min/mo. **Both are wrong,
and it was not landed.** Measured from real step timings: the redis-8 install
chain is 15-16s inside a 1,354s job, `ci`'s system deps 11s, the pip installs
2-5s. Across a whole pass that is under a minute and it does not cross a
rounding boundary. The `packages.redis.io` GPG fetch inside a required gate is
a genuine **third-party availability** risk and should be fixed for that reason
— it is not a money item, and dressing it as one would be the machinery-outruns-
value bias with a receipt attached.

## 5. What was NOT cut, and why

**`Cabinet script tests` — 1,088s, 30% of the entire bill in one step.** The
biggest honest target left, deliberately untouched. `pytest-xdist` is installed
nowhere in the repo. Hazards measured, outcome not: 14 files carry literal
`/tmp/` paths, 155 of 234 files shell out via `subprocess`, 68 touch one shared
Redis service container, and the 2026-07-28 profile found a long tail rather
than a hot spot (slowest 30 tests ≈ 350s of 811s). This directory holds the
killswitch, safety-switch and freeze fences — the code that must not be raced.
A parallelised suite that flakes converts a 61-catch sensor into a coin flip,
which is the sensor-vs-control defect this program has found ten ways, bought
for money.

**Cutover protocol before anyone lands it** (all four, not a subset):
per-worker `TMPDIR`; per-worker Redis DB index; 20 consecutive runs at
`-n 2 --dist loadfile` compared **id-for-id** against serial; and proof that the
parallelised battery still goes red on a deliberately re-introduced known
regression. `--dist loadfile` keeps most of the win if per-test distribution
proves unsafe. Note the runner is a private-repo standard 2-core, so the ceiling
is nearer 2× than 4× — verify `nproc` on the runner before quoting a number.

**`Dashboard vitest` — 361s.** Vitest already parallelises across files by
default and the config sets no worker cap, so the serialism is inside the tests
(`capture.test.ts` shells to python per frame). Root-cause it before quoting a
saving. Watch item, not a cut.

**`Hook regression harnesses` — 361s, 19 independent scripts in a serial loop.**
Parallelisable in principle; 62 literal `/tmp` references across 16 of the 19
harnesses have to move to per-harness `TMPDIR` first, and each harness must be
re-proven to still fail on its own re-introduced regression. This is the
enforcement plane's only regression net; fail-open here is the worst fail-open
available. Real work, not a flag.

**Nothing was moved to master-only or nightly, and that is a complete result.**
Branch protection is `strict: true`, so a red master is not a local event — every
open PR must merge master to stay mergeable, and on 2026-07-28 that meant 8
lanes and 134 runs. Meanwhile `tree-dedupe` has already reduced a matched master
push to one minute, so the master lane is where the money *isn't*. Moving a job
there buys a fleet-stall risk to save minutes that no longer exist. `gitleaks`
in particular must stay per-PR: post-merge secret remediation means a history
rewrite on a repo scheduled to go public.

**Deduplicating work inside the COG-4 gate.** `check-layer-separation.sh` runs
about five times per pass and the census about four; roughly half the COG-4
step is work `framework-tests` already did on the same tree in the same run.
Not touched. `verify-cognitive-phase4.sh` and the rollback rehearsal are members
of the frozen COG-4 review scope, so editing either breaks the
reviewed-bytes-equals-tested-bytes digest binding, and re-freezing the digest to
match new bytes would assert a review that never happened. The workflow runs the
twin verbatim on purpose: CI runs the command a captain runs, so a local green
and a CI green cannot disagree. Cheaper is available here; honest is not, yet.

**Fail-fast (dropping `if: !cancelled()`).** Failed job-runs are 1,286 min/month
(5.4%), so the ceiling is small, and the cost is one debugging round-trip per
red instead of the whole failure list at once. Keep the full-signal design.
