## 4. Envelope v2

### 4.1 Version dispatch — before the closed set, or every v2 send is refused

v1 `validate()` rejects any key outside ENVELOPE_KEYS (envelope.py:199-214) and `enforce()` is live fail-closed at 4 producer sites (server.py x3 wired-but-legacy; `task_event_emit` the only live typed lane). Therefore the FIRST check in the extended `classify_fields()` is version dispatch:

- no `"envelope"` field → `legacy_untyped` (grandfathered; byte-identical pass-through stays pinned by the existing test)
- envelope JSON without `schema_version` → v1 → frozen `validate()` (no semantic change; existing red-team suite is the regression gate)
- envelope JSON with `schema_version` → v2 → `validate_v2()` (new; same never-raise, names-not-values reason discipline, fail-closed-typed/fail-open-census direction, same `CABINET_ENVELOPE_ENFORCE`/`CABINET_ENVELOPE_REPORT` knobs)

No v1 constant, bound, or rule changes. `MAX_ENVELOPE_BYTES=16384` stays v1-only; v2 gets its own measured bound (§4.3).

The dispatcher is the single doorway for CONSUMERS too: `task-events-watch.py`'s `_valid_envelope` (:219-227) — the repo's only production caller of raw `validate()` — is re-pointed at the version-dispatching entry in the same wave (§3 disposition), because a v2 envelope fails v1's closed-set check by construction and the consumer poison-ACKs whatever it cannot validate (:273-284). Producer-side dispatch alone would leave the stream's only production consumer blind at cutover.
