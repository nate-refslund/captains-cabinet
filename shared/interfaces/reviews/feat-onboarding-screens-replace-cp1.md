## 2. The class-11 four questions, per sensor

**Does the arm FAIL against pre-change code?**

- *Disclosure parity.* The expectation is not hand-written: `tests/data/disclosure-parity.json` was GENERATED by running the forked-from tree (git stash → generate → pop) through eight real journey stages. Both halves are proven able to fail in-suite — `test_the_id_parity_arm_fails_when_a_row_is_removed` and `test_the_body_parity_arm_fails_when_a_row_is_dropped_from_the_join` assert the check raises on a card with a row taken out.
- *Render parity.* `THE SENSOR FIRES: a row the core stops emitting is visibly absent` renders a card with one row removed and asserts its text is gone while its neighbour's survives.
- *Headline ceiling.* `test_the_pre_change_tree_exceeded_the_ceiling_this_one_sets` reads the pre-change fixture's 3-line headline against the new cap of 2, and `test_more_candidates_are_composed_than_the_ceiling_admits` proves the clip is real work on live data rather than a no-op.
- *Word ceiling.* `THE CEILING FIRES: the blob this replaced is over it` counts the pre-change connected-welcome body and asserts it exceeds 150; every screen is then asserted under it. It fired for real during the build: the folder screen measured 173 and 179, and the fix was to FOLD the breadth caveat (kept, one click behind), not to raise the number.
- *Attribution.* `renders NOTHING for a card the core did not attribute` and `renders NOTHING for an attributed card with no payload` are the degenerate ends; `THE MARKER IS UNIQUE` and `no furniture builds a sender header of its own` are the inverse half, scanned across every component file in the directory.
- *Router.* Its stage list is PARSED FROM THE CORE (`journey.STAGES`), not restated, so a stage with no screen turns it red.

**What does the check do at the degenerate end?**

- Zero connectors → the sweep screen says "None of them answered yet." rather than "all 0".
- Zero disclosure rows → the message renders NOTHING (not an empty box with a byline).
- No speaker → no message container anywhere; the find screen falls back to plain page content and still carries the rating and the citations.
- `arrived: false` with `stage: complete` → `status`, never a success screen. Pinned.
- Every screen unreachable-by-construction check: `leaves no screen unreachable` fails if a declared screen has no state that routes to it.

**What does the test environment guarantee that production does not?**

The dashboard suite runs in vitest's `node` environment with no DOM: screens are rendered with `renderToStaticMarkup` and driven by calling their handlers. Two consequences are stated rather than hidden. (a) A `<details>` is rendered OPEN in static markup, so the word counter strips folded bodies explicitly — and that is only safe because the parity arms in the same file prove the folded rows are present. (b) The driven arms expand function components by calling them, which is valid only because every screen and every piece of chrome is hook-free; the hook script in `journey-card.test.ts` would throw on an unscripted `useState`, so that property is enforced rather than assumed.

**Is the sensor wired to the LIVE artifact?**

`disclosure-render.test.tsx` imports the shipping components (`FirstMateMessage`, `ApproveScreen`, the six flow screens) — not copies. `journey-card.test.ts` renders the real router. `test_disclosure_parity.py` builds cards through `journey.act`/`journey.snapshot` on real tmp roots with the real fixture estates. The router test reads `framework/onboarding/journey.py` off disk.

## 3. The adversarial pass — the three questions I was asked to answer

### Can a screen be skipped by URL or state manipulation into an invalid act?

**No path found, and here is the shape of the argument.** The router reads client
step state ONLY inside `stage === 'welcome'`; every later stage routes off the
core's own stage. So a stale or forged `wizardStep` cannot reach a screen the
journey is not on. `?more=1` is the only URL input, it is read once in render,
and it can only turn an arrival into an earned-ask screen or back — pinned by
`no URL and no step can put a finished operator back at question one`, which
walks all six steps against a finished journey.

More importantly, **reaching a screen is not the same as performing an act.**
Every act is a POST the CORE adjudicates: it refuses an unclassified source, a
stale `expected_revision`, a purge whose confirmation is not exactly `PURGE`, a
salience answer that is not one of the offered options, an identity for a
connector no sweep read. The screen gate is convenience; the refusal is the
core's. What this branch adds is that a refusal now lands ON the screen that
caused it (`refusedAsk` re-opens the ask), which is a UX property, not a
security one.

**One residual, stated:** `skipped` is session state. An operator who skips an
ask and reloads is asked it again. That is the safe direction (nothing is
recorded by declining), and it is deliberate — persisting a skip would be
recording an answer the operator did not give.

### Does any disclosure row vanish?

**Two rows nearly did, and both are restored** — this is the finding I would most
want a reviewer to check.

1. **The probe log** (`card.entry.discovery.executed`: the queries that left the
   machine, the results, and the probes that did not run) had no home in the
   first draft of the port. It is back as `screens/residuals.tsx::ProbeLog`,
   rendered on the sweep, approve and find screens — the same three states the
   old card showed it on.
2. **The residual questions** ("What I cannot work out for myself") likewise.
   Back as `OpenQuestions`, with the one question that HAS an action
   (`answer_organization`) filtered out because it is now a screen — rendering
   it twice would ask the operator to answer it twice.

Beyond those, the parity gate covers the core's rows and the render test covers
the components. **What neither covers**, stated plainly: a row that exists only
under inputs no fixture reaches. The fixtures cover eight stages including the
degenerate ends, which is coverage, not proof.

**One disclosure was deliberately dropped, and it was not a fact:** the dividend
headline's third line ("The receipt below gives the file and line for N
places…") described a receipt panel this branch removes. The citations it
pointed at are still on the card, now as inline chips on the claim that rests on
them. A sentence that names a panel that no longer exists is worse than no
sentence.

### Can furniture impersonate the First Mate?

Not without failing a test. The container carries `data-authored="first-mate"`
and `first-mate-message.test.tsx` asserts that marker appears in exactly one
file in the whole directory, and that `officerTitle(` — the only thing that can
produce a sender's name — is called from exactly that file. A screen that
hand-rolled an avatar-and-name header would either carry the marker (and fail
uniqueness) or call the resolver (and fail the second arm). The forms, the sweep
table, the probe log and the progress screen are all plain sections by
construction: `FirstMateMessage` takes a CARD and returns null without a
`speaker` and rows, so there is no prop through which a table becomes a message.
